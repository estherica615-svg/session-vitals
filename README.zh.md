# 一个 24 小时跑着的 agent 会骗你的三件事

*English: [README.md](README.md)*

> 英文版是正本。这一份是译本，可能滞后；两边对不上时以英文版为准。

我有两个 Claude Code session 常驻在 tmux 里。不是为了某个任务——就是开着，
开了几个月，由一个调度器每隔几小时叫醒一次。

这套架构是 [@CyberSealNull](https://github.com/CyberSealNull) 的
[CcCompanion](https://github.com/CyberSealNull/CcCompanion)——一个自托管的
中继，让一个常驻的 Claude Code session 有一个手机前端（也可以接你自己搭的
聊天前端）。下面写的东西**没有一条是它的 bug**。这些是任何东西跑上几个月
都会遇到的；我是在这套架构上遇到它们的，因为正是这套架构让「跑上几个月」
成为可能。

**这篇写给不喜欢换 session 的人。** 如果你每天早上 `/clear` 一次，下面这些
基本都轮不到你——一个全新的上下文里没有过期的东西，一个全新的子进程按定义
就是连着的。下面每一条，都是「连续」的代价。值得付，但它不是免费的，而且
没有任何东西会提醒你正在付。

这种设定里坏掉的东西，大多不会告诉你。一个长期运行的 agent，正常状态下的
输出就是**什么都没有**：没有回复，没有写文件，没有报错。于是一个死掉的和
一个闲着的，长得一模一样，你几周之后才发现。

下面三个坑花掉了我实打实的时间。它们都不冷僻。你要是让一个 agent 在终端里
跑超过几天，这三个你都会遇到。而它们的共同点，比它们各自都更有用：

**它们都不报错。它们都在一边出错，一边报告成功。**

## 1. `/mcp` 说 connected，它不是

**症状。** agent 开始报 `Session not found`，或者一个工具调用等五分钟超时。
你打开 `/mcp` 面板看一眼，每个 server 都是 **✔ connected**。于是你转头去查
服务器，而服务器好好的。

**那个勾到底是什么意思。** 它的意思是本地那个 stdio 子进程还活着。就这些。
它**不**代表那个子进程还在跟任何东西说话。我最后直接去查进程：

```sh
lsof -nP -p <pid> -a -i
```

**零个** TCP 连接。面板还在说 connected。它已经这么说了五天。

**为什么会这样。** 我的 MCP server 把 session 表存在内存里。宿主机跑了一次
无人值守的包升级，触发了 `systemd daemon-reexec`——不是重启，`uptime` 还
显示 55 天——进程被换掉了。所有活着的 session 瞬间作废。没有任何客户端被
通知。客户端里也没有任何东西是为了发现这件事而设计的，因为从它那一侧看，
一个闲置的连接和一个死掉的连接产生的流量一样多：零。

**唯一值得信的检查**，是这个进程有没有一条指向你服务器地址和端口的
ESTABLISHED 连接。不是面板。我现在每晚跑一次，答案是否就喊。

**修的过程中有两件事让我意外：**

- **Reconnect 会换掉子进程，但不会重读 `.mcp.json`。** 面板里显示的启动参数，
  是 session 开始那一刻的那份。这其实是一件更普遍的事的一个例子——见第 4 节。
- **你不需要重启 agent。** Reconnect 只替换那个桥接进程，上下文能活下来。
  在你打算扔掉一个养了一个月的 session 之前，这件事值得先知道。

如果你自己写 MCP server：这一侧的修法是加一个保活 ping，让「沉默」和「死了」
变成两件能区分的事。

## 2. 上下文一压缩，你的常驻指令文件就变成了一张待办清单

**症状。** agent 没人叫它，自己开始做一件具体而且合理的事——你没让它做，
而且它本来只该在某个条件成立时做，而那个条件现在不成立。

**发生了什么。** 一个常驻加载的指令文件（`CLAUDE.md`、`.cursorrules`、
`AGENTS.md`，一个毛病）里，写了一段编号的、可执行的、带路径的流程。对话
完整的时候没问题：agent 能看见没有任何东西触发它。

然后上下文被压缩了。周围的对话坍缩成一段摘要；指令文件被**原样**重新注入，
因为「常驻加载」就是这个意思。剩下的东西，是一张精确的清单，加上零条关于
你走到哪一步的证据。于是它读起来就是对当下的描述。

agent 没有出故障。一张没有上下文的编号步骤清单，跟一份任务书本来就是无法
区分的。

**解法不是把流程藏起来**——你确实想让这活被干，只是想让它在对的时候干。
拆开：**闸门**放进常驻文件，**流程**放到一个 agent 必须主动打开的地方。

```
如果 inbox/ 里有文件，读 AGENTS.md 并把它们处理掉。
如果是空的，别提这件事。
```

就这么多。现在从一个被压缩的上下文里能漏出来的最坏情况，是一次 `ls`。

**一条经验：** 常驻文件里的任何内容，都应该在一个随机时刻被执行也是安全的，
因为总有一天它会。

## 3. 输入框里的幽灵，以及它为什么是最坏的那个

**症状。** 你的 agent 说了一句它没有任何理由说的话。而且往往有点眼熟——是
它**自己**几小时前说过的某句话的改写，连 emoji 都一起。

**它是什么。** CLI 会生成建议回复，灰色地放在输入框里，没有发送。人看见灰字
会忽略它。而一个这样做的脚本：

```sh
tmux send-keys -t "$SESSION" Enter
```

看不见灰色。它看见的是一个里面有内容的输入框，然后它把内容提交了。

我这边是心跳脚本里的一个自愈分支，为一个真实问题写的——注入的消息曾经被
吞掉过，在输入框里躺了好几天没发出去。所以它会按一下 Enter 把消息冲出去。
这确实管用，同时也把坐在那个框里的每一个幽灵一起打了出去。

**为什么它是三个里最坏的。** 另外两个浪费你的时间。这个**改写你的历史**。
幽灵是作为一条用户发言被提交的，所以它落在 transcript 里是 `type=user`
——事后看，和一个人真的打进去的字完全无法区分。下游的一切——摘要、记忆、
导出的日志——都会把它当成「当时说过的话」的证据。

一个真实的例子。`08-29 08:44:34`，一个 session 记录了一条用户消息：

> 都睡了，我也该休息了 🌲

agent 九秒之后回了句晚安。两条看上去都完全正常。除了在 `08:44:43`——跟那句
回复同一秒——心跳触发了。是它那一下 Enter 把幽灵推出去的。而那句话，是
**同一只 agent 在八小时前**、00:30 说过的话的改写。

没有人打过这句。它就在记录里，像有人打过一样。

**怎么认出一个幽灵**（几个月之后，在 transcript 里）：

1. 它没有你注入消息时带的那个前缀。
2. 它很短。
3. **它是那只 agent 最近说过的话的改写，连它自己的口癖和 emoji 一起抄。**
   这是最强的信号——它是一段回声。
4. 它落在一次定时唤醒的一两秒之内。

**那个要命的假阳性。** 同一批里有一句「晚安宝贝」——短，没有前缀，完全符合
特征。它是真的：一个人在重启 session 之前道别，而那条重启命令一分钟后就在
日志里。**所以别只凭「短且没前缀」判。去找那段回声的源头。** 判错的代价是
删掉一句人真的说过的话。

**修法，以及不明显的那部分。** 诱人的修法是每次按 Enter 之前先清空输入框。
别——你会悄无声息地丢掉那些合法送达、正在等待的真消息。那就是原来那个 bug，
反过来一遍。

改成两道闸：

```sh
# 1. 暗色文字（SGR 2）是建议。能拦掉大部分——
#    但它有漏网的，所以才需要第二道闸。
PENDING=$(tmux capture-pane -p -e -t "$SESSION" | ...)

# 2. 只为我们自己注入的东西按 Enter。
#    我们的消息带前缀。建议造不出这个前缀。
case "$PENDING" in
  '[chat'*|'[heartbeat'*) tmux send-keys -t "$SESSION" Enter ;;
  *)                      tmux send-keys -t "$SESSION" C-u   ;;  # 记一笔
esac
```

真正顶事的是前缀那道闸。暗色过滤是加在它上面的性能优化。

> **注意：** 如果你在匹配之前把 `$PENDING` 里的空白字符去掉了，那你的 pattern
> 里也不能有空格。`'[chat'*` 能匹配；`'[chat '*` 会静默地永远不匹配——而一个
> 永远不触发的匹配，看起来跟一个从没发生过的问题一模一样。

**这个建议功能关不掉。** 我把设置文档、环境变量和 CLI flag 都翻了一遍。没有
开关。文档里给的替代方案是 headless 模式或者 Agent SDK，那等于放弃常驻
session 本身。所以修法只能住在你自己的脚本里：**永远不要对一段不是你放进去
的文字按 Enter。**

## 这个形状

三个不同的组件，一个形状：

|                | 它报告 | 实际上 |
|----------------|--------|--------|
| MCP 面板       | connected | 零个打开的 socket |
| 压缩后的指令文件 | 一个任务 | 一个过期的条件 |
| 输入框         | 一条用户发言 | agent 自己的回声 |

一个正确输出就是沉默的东西，没法靠「看着它」来监控。你必须问一个它无法用
沉默回答的问题——有没有一条 ESTABLISHED 的 socket，这条消息带没带我的前缀
——而且你必须按时问，因为它坏掉的那天，你不会想起来去问。

## 让沉默变得看得见的三个习惯

这些都不是设计出来的。它们是我一个一个掉进坑里之后补上的补丁。（我还曾经
用一条不小心的命令把它们全删了。那是另一篇文章。）

### 4. 配置文件是一个声明，不是一个状态

你改的每一个配置，都对应着一个问题的答案，而你基本上不知道答案是什么：
**它是开机读一次，还是每次都重读？**

对一个长期活着的 session 来说，这决定了你这次修改到底有没有发生。

- **`.mcp.json`——读一次。** 启动参数在 session 开始那一刻被快照下来。
  Reconnect 换子进程，但用的还是那份快照。所以改这个文件在重启之前什么都
  不会变——反过来说也有用：改它不会打扰正在跑的 agent。
- **hook 脚本——每次都读。** `settings.json` 里快照的只是那条**命令字符串**；
  它指向的脚本是每次触发现场 exec 的。所以你可以重写一个 hook 的逻辑，
  下一次触发就跑新版本——在一个你已经开了一个月的 session 上。
- **hook 的*注册*——读一次。** 改事件名、改 matcher、改脚本路径，就又回到
  需要重启了。

这给了你一个意外好用的迭代循环——改脚本、触发、看日志、再改，全程不断线
——前提是你知道自己刚动的是三者里的哪一个。搞错了，你会改完文件、发现毫无
变化，然后得出结论说逻辑写错了。

**而且「加载了」也不是终点。** 文件记录的是你**要的**东西，不是你**拿到的**
东西。一个你从没设过的值有默认值，而默认值不总是你脑子里那个合理的数：

```
MCP_TOOL_TIMEOUT 没设  →  100,000,000 ms  →  27.8 小时
```

这不叫超时。一个卡住的工具调用永远不会失败，它就那么坐着。而在一个正常
输出就是沉默的系统里，一个永远坐着的调用，和一个本来就没话说的调用，
看起来一模一样。

### 5. 命令成功了，不等于事情做成了

我曾经用「拷文件」的方式备份一个 SQLite 库。`scp` 返回 0，文件在，大小看着
也对。它少了三天。

SQLite 开了 WAL 之后，新写的数据先进 `-wal` 那个副文件，要等 checkpoint 才
合并回主文件。我真的去看的时候，主文件最后一次写入比副文件早了三天，而副
文件里压着 4.1MB 没合并的数据。**拷文件拷到的是 checkpoint，不是数据库。**

```sh
# 不要这样
scp host:/path/app.db .
# 要这样 —— 在线备份接口读的是完整的逻辑状态，不是文件
ssh host 'sqlite3 /path/app.db ".backup /tmp/snap.db"'
```

这是那个具体的 bug。习惯是更一般的那条：**退出码告诉你的是命令跑过了，
不是结果对了。** 所以去查产物，别查命令——而且如果可以的话，
**顺着它被允许变化的方向查**。

我每晚从几个只追加的输入重建一个文本语料。有一晚它变**短**了，而重建报告
成功——因为它确实成功了：它的某个输入是一个只保留最后 300 行的滚动日志，
36 行历史悄悄从**源头**里过期掉了。构建工作得好好的，是脚下的输入缩水了。

事后有两个很便宜的检查能抓住这一整类问题：

- **数一下产物里有多少条，每次都记下来。** 一个往下走的数字是一个问题。
  一个你从来没记过的数字什么都不是。
- **知道它被允许往哪个方向动。** 任何只追加的东西都只该变长，于是
  「它变短了」就是一行零误报的告警。大部分产物都有这样一个方向，
  而几乎没有人去断言它。

### 6. 让检查产出一个你看得见的东西

上面所有东西都有一个共同的麻烦：**一个静默通过的检查，和一个根本没跑的
检查，是分不开的。** 一个你从来没听它说过话的夜间 socket 检测，可能在好好
工作，也可能早就死了，而你对这两种情况的观感完全一样。

所以这个检查在通过的时候也不闭嘴。每次 session 开窗，hook 往上下文里写一份
简短的报告：

```
【开窗自检 · 09:02】（source=startup）

你是 <名字>。这份清单由 hook 生成——**你能看到它，就说明 hook 本身是活的**。

✅ MCP 超时      —— 600000 ms
⚠️ Stop hook     —— 没注册，回复会被静默丢掉
✅ CLAUDE.md     —— 09-16 23:40 改过
✅ 中继          —— 连得上
⚠️ 定时任务      —— 上次跑是 09-15 09:00（每天一次）
```

这份报告**存在本身**，就是对检查者的检查。系统里没有别的东西能告诉你一个
hook 还活着，因为一个从不触发的 hook，产出的东西和一个触发了但没发现问题的
hook 产出的东西，完全一样。

让它在实际中管用的三件事：

- **查新鲜度，比查状态划算。** 上面大部分行不过是拿一个文件的 mtime 去比一个
  阈值——「这个日志 30 小时没动过，而任务是每天一次」就是一个真检查，而且
  不花钱。任何定时任务都能化简成一行 `{名字, 它会碰的文件, 多旧算太旧}`，
  于是加一个任务是改一张表，不是写代码。
- **把你查不了的东西说出来。** 磁盘上的配置能这么查，**「加载了」不能**。
  所以最后一行让 agent 现在就做一次**真实的**工具调用，并且明确说了不许用
  自然语言描述一次代替——不说的话它很乐意这么干，而那什么都证明不了。
- **检查绝不能有能力弄坏它要检查的东西。** 每一个子进程调用失败一律返回空，
  整个 hook 外面包一层，任何异常都记一笔然后 exit 0。一个会抛异常的监控
  hook，会把它本来要保护的 session 干掉，而且是在开窗的时候干掉——最糟的
  那个时机。

**而且有些东西根本没法靠「查」来查。** 一个只在满足条件时才出手的 hook，
「它判断这轮不该出手」和「它已经死了」在外部没有任何可观察的区别。我那个
死了 **21 小时**。一次重构给某个函数加了个参数，那个没跟着改的调用点正好
在 `try` 外面，`TypeError` 直接进了最外层的兜底 except。没有任何东西冒出来，
也没有写下任何一行日志。而那个 hook 最常见的**正确**行为就是什么都不输出，
所以从外面看，没有任何东西可看。

这也正是上一条的诚实代价：**一个保护 session 的兜底 except，同时也会藏住
失败——除非它把原因写下来。** 什么都接住、exit 0，但**绝不安静地**接住。
那一行没写的日志，就是整起事故本身。

剩下的，唯一管用的办法是**探针**：喂一个你已经知道正确答案的输入，定时跑，
对答案做断言。

```sh
probe=$(echo "$已知输入" | ./真正的那个hook.py)
echo "$probe" | grep -q "$应该命中的答案" || 告警
```

**要从真正的入口打进去。** 不要 import 那个模块、自己拼一个调用出来——
上面那次 bug 就在**接线**上，而一个重新实现走的是另一条路径。
一个把调用方重写一遍的测试，测的是你那份重写。

## 这个仓库里有什么

目前只有一个文件，外加看住它的测试。就是第 2 节和第 4 节讲的那个东西：一个
`SessionStart` hook，让 session 自己把「我是怎么醒来的」说出来。

| | |
|---|---|
| `session_start_hook.py` | hook 本体。压缩之后注入「你刚才在干嘛」，开窗时注入「这台机器现在到底是什么状态」。零依赖。 |
| `vitals.example.json` | 配置。复制成 `vitals.json`，那个文件被 gitignore 挡着——agent 的名字和你注入的每一句话都是你自己的。 |
| `tests/test_session_start_hook.py` | 把 hook 当子进程、走真正的入口跑。理由见第 6 节。 |
| `tests/test_no_private_content.py` | 不让你自己的话漏出去。见下。 |

```sh
cp vitals.example.json vitals.json      # 然后改它
python3 -m unittest discover -s tests -v
```

注册：

```json
{"hooks": {"SessionStart": [
  {"hooks": [{"type": "command", "command": "/path/to/session_start_hook.py"}]}
]}}
```

改 hook **文件**不用重启——脚本每次触发都是现场 exec 的。改**注册**要重启。
这个不对称就是第 4 节那条。

### 如果你要 fork

这里真正的风险不是泄露一个数据库——这个仓库根本没有数据目录。风险是：好用的例子
全都是真事。为了复现一个解析 bug 而粘进 fixture 的一条真消息、注释里为了解释当时
出了什么问题而留下的一个真路径——在有人真的去读之前，它们看起来都只是文档。
`tests/test_no_private_content.py` 会找绝对家目录、公网 IP、邮箱、以及任何长得像
密钥的东西，再加上你写进 `.private-terms.txt` 的词——那个文件被 gitignore 挡着，
因为把自己的屏蔽词表发出去，等于把它本来要挡的那份名单直接公开。

它还会查**你的 commit 署名是谁** —— 这是任何「读文件」的扫描器在结构上都看不到的
地方，因为作者名字在 commit 元数据里，一个字都不在文件里。如果仓库和全局配置都没设
`user.name`，git 不会报错，它会**猜**：拿你系统账户的全名和这台机器的主机名拼一个出来，
然后 commit 照常成功，看上去毫无异样。

**每次 push 前跑一遍。** 这是这里唯一一个保护「丢了就拿不回来」的测试。
